What this is
Problem: no one can see, per operator, whether Bradbury accepts transactions at the first attempt or why it retries.
Users: validator operators, developers deploying contracts with LLM calls, and the GenLayer team.
Use: spot degraded operators and measure the real cost of LLM calls against a control.
1. Sources
History on this page starts on 2026-10-01. Earlier measurements are in Model validation.
[NET] Network
All transactions on Bradbury, read from consensus events. Contracts and inputs are not ours. Updated every minute. Since 2026-10-01.
[CAMP] Campaign
Our daily campaign: fixed reference contracts and a control without LLM. All four reference contracts run together in the same one-hour window each day, so the control sees the same network conditions. Runs once a day at a rotating hour, so every hour of the day is covered over time. Only transactions sent by the campaign wallet to a reference contract count as campaign. Since 2026-10-01.
[CHAIN] Chain
Read directly from the staking contract. Epoch changes are read every minute. The validator lists (active, banned and quarantine records) are read every 5 minutes and whenever an epoch starts. Stake and declared name are read for a few validators every minute, the ones read longest ago. Since 2026-10-01.
2. How we count
First-attempt acceptance
A transaction counts as accepted at the first attempt when its first real acceptance comes after a single proposal, with no leader timeout, leader rotation, appeal, recomputation or validators timeout before it. A round counts as an acceptance only when its result is AGREE: the chain also closes a round on a validators timeout. The final state decides, so an acceptance overturned by an appeal counts as no consensus. A round that ends without an acceptance stays in progress until the transaction is finalized, because a rotation or an appeal can still follow; a transaction finalized with no acceptance counts as no consensus. Each vote belongs to the attempt whose committee contains the voter.
Why we count from consensus events
Since 2026-10-01 the page counts from the consensus events of each transaction, not from polling its status. Polling every second does not see a leader that times out in under 3 seconds, so it counts some retried transactions as first attempts. In the September 2026 validation this changed 7 of 728 transactions.
Created and queued
A transaction that enters consensus as soon as it is sent emits one event. One that has to wait behind earlier transactions of the same contract emits one event when it is sent and another when it enters. A transaction counts as created when it enters consensus: its epoch, its hour and its time to acceptance start there. One that was sent and has not entered consensus is queued: it counts as in progress, in the epoch of the block that sent it, and moves to the epoch where it enters. One cancelled before entering ends as no consensus. The wait in the queue is in the data files (queue_seconds).
Retry causes
Leader timeout: the leader of the attempt did not deliver a proposal in time, and a new leader was activated.
No majority: the votes did not give the proposal a majority, and the leader was rotated.
Appeal: a larger committee rechecked the existing proposal. We see one start right after a validators timeout.
Recomputation: the transaction was sent back to be executed again, after a successful appeal on it or on an earlier transaction of the same contract.
Health labels
[HEALTHY]: first-attempt acceptance of 90% or more. [DEGRADED]: 70 to 90%. [FAILING]: below 70%. Fixed thresholds chosen by Probe.EXE, not a GenLayer standard. The labels apply to acceptance rates only, never to an operator.
Vote categories
█ Agree: the validator's result matched the leader's proposal.
█ Content disagreement: the validator ran the contract and reached a different result that fails the contract's equivalence rule.
█ Execution divergence (DV): the validator's execution did not reproduce the leader's result (a deterministic violation), which is different from disagreeing with its content.
█ Timeout: the validator did not submit a vote before the deadline.
Attribution per operator
Every vote and every leader round is attributed to the validator address that cast it, then shown with the operator name declared on chain.
Eligible validators
A validator counts as eligible when it is in the active list of the staking contract, not in its banned list and with no quarantine in effect. The eligible set is stored each time it changes and at each epoch change, and each campaign transaction is compared with the set in effect at its block. The GenLayer documentation says that a ban or a quarantine prevents new selection. Measured: the quarantine list of the staking contract keeps entries after they expire. An entry "until epoch N" stops applying when epoch N starts: in epoch 168, validators listed with a quarantine until epoch 168 voted and led. Expired entries are ignored, here and in the quarantined count.
Too few votes to compare
An operator with fewer than 10 votes on campaign contracts with LLM calls in the view is shown as "Too few votes to compare" and is never marked [ABOVE REST].
Stalled contracts
A contract is stalled when five transactions in a row received no vote and the fifth one is over 60 minutes old. A transaction that stays idle or queued counts as one without a vote. The contract recovers at the next vote on any of its transactions.
Campaigns
A campaign is running while one of its transactions had an event in the last 10 minutes. Campaign transactions created more than 30 minutes apart belong to two campaigns. A day counts as a failed campaign when its 3-hour slot ended more than 30 minutes ago and no campaign transaction was seen in it.
RPC incidents
An incident opens when two runs of the collector in a row get an answer from the RPC that is not JSON, and closes after five clean runs. Other errors are not counted as incidents.
Stale data
A block is marked [STALE] when its source has not been updated for longer than expected: 10 minutes for [NET] and [CHAIN], 30 hours for [CAMP].
Intervals
Rates come with a 95% Clopper-Pearson interval, an exact binomial interval. It stays valid for small counts, where it is wide.
Detecting contracts with LLM calls
A contract is labeled "with LLM calls" when its code on chain contains exec_prompt, prompt_comparative or prompt_non_comparative. Limit: the label applies to the contract, not to each transaction. A labeled contract can run code paths without an LLM call, and contracts whose code we cannot read are shown as "Code not available".
3. What we cannot see
The model, provider or GenVM version of each validator is not visible on chain. We measure symptoms per operator, not their causes.
Third-party contracts: we do not control their code or inputs. Testnet: node or contract upgrades can change behavior.

5. Limits
- Bradbury is a testnet. Validator software and contracts can change without notice.
- The campaign covers four fixed contracts. It does not represent every contract.
- One campaign a day gives about 80 transactions per contract, so intervals are wide.
- There are no alerts in this version.
- The latency of transactions that cross an epoch change is not reported yet.
- Transactions accepted with an execution error are not counted apart: consensus events do not carry the execution result, so they count as accepted.
- Network counts depend on the RPC. Gaps in RPC data are listed in Events.
- Operator names are declared by the operators on chain and are not verified.
6. Public API
Every number on this page comes from a read-only JSON API on this same address. It needs no key and can be called from any origin. It returns counts and rates. Intervals are not included: compute them from the counts (Clopper-Pearson, stats.js).
Views
Endpoints with view take view=epoch:168 (one epoch) or view=24h (the last 24 hours). Without it they answer for the current epoch.
Endpoints
GET /api/meta: last update per source, current epoch, list of epochs, RPC state.
GET /api/tape: the last 40 network transactions with their result.
GET /api/overview?view=: first-attempt acceptance of the campaign (with LLM and control) and of the network, votes by type, retry causes, time to acceptance, validator counts, last campaign.
GET /api/contracts?view=: reference contracts, every contract of the network with its LLM label, and stalled contracts.
GET /api/operators?view=: one row per validator: votes by type on campaign contracts with LLM, on the control and on the whole network, leader rounds and leader timeouts, status, stake, selection weight, first-leader counts against the expected ones, and a series by epoch.
GET /api/events?view=&type=&before=: the event log, 50 per page. type is one of epochs, validators, contracts, campaigns, rpc. before is the next value of the previous page.
GET /api/status: the last block the collector stored and its last ten runs (range read, requests to the RPC, errors).
GET /api/badge/{contract}.svg: an image with the first-attempt acceptance of a contract in the current epoch, to embed in a README or a page. Contracts has a [badge] button on each network contract that copies its Markdown.
GET /api/export?epoch=&after=: every transaction of an epoch with its attempts and votes, 200 per page. after is the next value of the previous page. The columns are documented in the README of the repository.
Cache and limits
Responses are cached: 60 seconds for /api/meta, /api/tape and /api/status, 300 seconds for the rest. Requests answered from the cache are not limited. Requests that are not in the cache are limited to 120 per minute from one address. Over the limit the API answers 429 with a Retry-After header. For bulk use, take the daily files of the data branch instead.
